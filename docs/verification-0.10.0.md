# Hext 0.10.0 verification

Observed locally on Windows 11 with MinGW-w64 and an authenticated Codex CLI on November 19, 2026. Tests use generated data and owned fixture applications. A fixture is not presented as a real service account, and an accepted command is not presented as a verified final effect.

| Area | Observed result |
| --- | --- |
| Native build | The C++17/Win32 application built successfully with the additional Windows system libraries. No embedded web runtime or new downloaded agent framework was introduced. |
| Existing regressions | Console tests passed for motion, spring profiles, visibility, desktop-region coverage/recovery, presentation, material/color, hardware formatting, subprocesses, audio selection, shortcut models and the personal-assistant core. Both existing hidden native renderer/controller reports ended with zero failures. |
| Real provider goal | The authenticated Codex generated a PowerShell SHA-256 calculation for a random string, executed it through Hext's actual AppContainer tool, used its returned hash in another native Windows process, invoked the fixture's Apply button, observed the resulting text, and started the dependent one-minute Hext timer. Six tool dispatches and six provider rounds completed. An independent Windows BCrypt digest and cross-process control reads matched the actual result. There is no dedicated hash/task command in Hext's catalog. |
| Actual UI Automation | Read controls in an owned unelevated Win32 application, excluded its password value, entered text and read it back, rejected stale observations, invoked a button and observed the resulting application state separately. UI APIs run in the actual bounded worker process. |
| Permission enforcement | The actual controller required window consent before reading controls, then respected the configured autonomy approval. A denied desktop grant prevented text entry even when passed an obsolete approved flag. Package installation remained Confirm under generally allowed autonomy and Denied with its category revoked. Existing one-use/replay/revision/service/tool tests passed. A stale UI approval stopped execution and retained the original goal instead of silently completing the task. |
| Configuration and continuation | The controller waited for actual accessible state in the owned application, observed the fixture's completion, and started its queued real timer with the original goal unchanged and no additional user message. This tests the general intervention mechanism; it is not an external account login. |
| Isolated script boundary | A real PowerShell script wrote/read its own file and retained it across a second invocation. Windows denied the generated private-canary read, external write, and outbound socket connection (10013). The disposable AppContainer profile deletion returned success. No unrestricted fallback ran. |
| Web research | The native HTTPS broker fetched the Microsoft UI Automation documentation with HTTP 200. Bing RSS search returned HTTP 200 and eight links. Loopback/private-address and credential/port/scheme checks rejected unsupported inputs. Redirects were not followed. |
| Package preparation | Located signature-verified Microsoft App Installer, checked the official WinGet community source, searched its actual index and inspected a pinned Microsoft.PowerShell version returned by that index. An opaque proposal was created. Altered review metadata was rejected before the installer branch. No program was installed for validation. |
| Durable tasks | The actual controller checkpointed in-flight work, preserved a paused task across repeated cleanup, reopened the original goal, discarded approval, and recorded the interrupted effect as uncertain without replay. A separate fresh Windows process also restored the encrypted chat, memory, language, grants and in-flight task as paused. |
| Error handling | Owned-child timeout/cancellation passed. An unsupported native control operation was rejected before any effect, followed by a supported operation. Stale targets were rejected. UI failures after an attempted effect are classified as uncertain and stop automatic recovery. Known recoverable failures may return to planning within the global budget. |
| Authentication failure | An actual Spotify TLS request with an intentionally invalid test token returned 401 without playback changes. No successful account or playback was fabricated. |
| Running application | Hext 0.10.0 was deployed with its existing configuration preserved; the executable hash matched the verified preview. Live shortcut message paths, topmost cleanup, independent hide/show, and three desktop coverage/exposure recovery cycles passed without injected keys or screen capture. |
| Native visual inspection | Window authorization, intervention, pending-task and action-detail frames were exported from Hext's own DIB and visually inspected. Controls remained named, unique and within island bounds. Existing native controls/material/motion were reused; no desktop recording was used. |

Two issues were found by integration testing rather than compilation: the GUI worker entry point initially failed to recognize a quoted argument, and the old two-read duplicate limit stopped legitimate repeated UI observations. Windows argument parsing and a bounded sixteen-observation allowance corrected these; ordinary write-duplicate protection remains in place. The verification harness also uses actual cross-process control messages rather than relying on another process's cached window text.

## Not verified or intentionally bounded

- A successful third-party installation was not executed. The real source/query/proposal path, review-change rejection and permission decisions were verified; installer completion, EULAs, UAC and each package's user-scope support need package-specific testing. Stopping an installer cannot guarantee that an external service has not accepted effects.
- No successful Spotify OAuth/Premium API playback or Claude login/inference was performed. These still require the user's installed provider/application, account configuration and applicable platform access. The existing dedicated adapters remain available.
- The UI test uses an actual owned Win32 application, not private user apps or an external authenticated website. Browser/third-party coverage depends on accessible controls. There is no full DOM automation, screenshot/coordinate fallback, arbitrary MCP server loader or universal desktop control claim.
- General UI effects always require explicit action approval. Protected/elevated windows, password controls and known command/administration/Spotify surfaces are excluded. A third-party application's downstream effects cannot all be classified semantically by Hext.
- Terminal scripts are general inside their own AppContainer. Personal folders, host administration and network are not granted. Resource limits include job memory, process count, output and time; there is no hard disk quota. Explicit file tools remain bounded and do not become unrestricted terminal filesystem access.
- Tasks resume explicitly with fresh checks, not by automatically replaying writes after startup. There is one pending goal per conversation and at most twenty pending conversations/workspaces. Saved conversations and memory remain separate from the bounded task checkpoint.
- Broader Windows 10, device/DPI, application and accessibility-user coverage remains outstanding. See [general agent boundaries](agent.md) and [development checks](development.md).

The release workflow runs account-free build/regression checks; live account-dependent tests are local opt-ins. Private settings, databases, fixture executables, provider output and generated images are excluded from releases and version control.
